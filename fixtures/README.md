# Database fixtures and verification

`OriginalSample.accdb` is a genuine Access 2010-format ACCDB created by Jackcess, containing Customers and Orders with AutoNumber primary keys, an enforced relationship, money, dates, NULLs and Unicode. `Practice.accdb` demonstrates edited data plus a native Practice table and secondary index. `OriginalSample.mdb` is a genuine Jet4 Access 2003-format sample, independently exercised through the same copy/query/edit/reopen lifecycle. Open them through the app to create a new protected working copy.

`NativeQueriesExperimental.accdb` contains two native SELECT query objects made by the explicitly experimental catalog writer: CitySummary and NamedPeople. Jackcess reopens them as native SELECT objects and JDBC executes them by saved name after the internal mirror is reloaded. Actual Windows Access verification remains pending.

`queryV2010.accdb` is the pinned Jackcess upstream fixture with nine native query definitions: select, append, delete, update, make-table, crosstab, union, DDL and pass-through. Reading those definitions is tested. Executing its existing SELECT SQL is tested. Unrelated table DDL preserves all nine queries on native file reopen. The driver cannot materialize the fixture's duplicate-named SELECT columns as an internal view, but executing its SQL directly succeeds; logs record that engine warning. This does not establish broad saved-query execution parity.

`complexDataV2010.accdb` contains attachment, multivalue and append/history fields. These fields are detected, the whole copy is restricted to read only, and reads succeed. Advanced-field design/edit/export are unimplemented.

`db2007-enc.accdb` is a Jackcess Encrypt fixture used only to prove explicit encrypted-file refusal. Its password is not requested or used. No encrypted database is claimed readable.

`upstream.lock` pins the upstream fixture digests and source URLs. `verification.txt` is the integration run output. Rerun `scripts/test.sh` from the project directory (offline after the pinned jars are present). Tests create disposable native files under `../../work/database-proof` and retain them for inspection; supplied fixtures are never modified. `--publish-fixtures` creates the two generated deliverable files only if absent.

Native query creation via UCanAccess CREATE VIEW fails with SQLFeatureNotSupportedException. A separate, explicitly experimental writer now uses pinned Jackcess QueryFormat/SelectQueryImpl native catalog rows for a conservative subset: one local outer table SELECT, DISTINCT, AS aliases, WHERE, GROUP BY, HAVING and ORDER BY. Joins, UNION, TOP, native parameter-query saving and action-query saving are refused. `saveQueryExperimental` is exposed only with the experimental UI label; default `saveQuery` requires `-Daccess.experimentalNativeQueries=true`. Each write closes the JDBC mirror, creates a new verified pre-query backup, writes the native file, independently reopens/query-checks it and reopens the mirror. Existing native query definitions are checked unchanged. Injected partial-backup and post-write failures prove that intact files are never replaced by partial backups and that mutation failures restore exact pre-save bytes. This is native catalog persistence, with Windows Access verification still pending.

SELECT INTO translates to the engine's supported native CREATE TABLE AS (SELECT...) WITH DATA. It does not copy indexes/relationships and its inferred types have not been exhaustively compared to Windows Access. Bound make-table parameters are refused. CREATE TABLE, ADD COLUMN, CREATE INDEX, DROP TABLE and ALTER TABLE ADD FOREIGN KEY are tested, along with native defaults and required fields. DROP COLUMN is unsupported and leaves schema unchanged.

Named Access PARAMETERS declarations and positional `?` values execute through prepared statements; Text, integral values, Currency/decimals, DateTime, boolean and NULL binding are supported. Integral conversions reject overflow and fractional truncation. Prepared record insertion, editing and deletion require known scalar fields and a complete native primary key; primary-key and AutoNumber editing are blocked. Comments, external IN databases, engine/Java routines and system-table mutation are blocked by the editor gate. Results are capped at 5000 with a visible truncated flag; experimental native saving refuses truncated verification.

Each working-copy session creates `<working-filename>.original-backup`, containing the exact original bytes. Original, copy and backup hashes are compared, then compatibility inspection runs against the actual working bytes and rehashes them before the JDBC connection opens. The working file must retain the original format extension. Existing copies and backups are never replaced. Copy edits persist immediately through UCanAccess; Save/flush flushes the native file. Recover the opening state by copying the backup to a new .accdb filename. Reopen a working file by selecting it as a source and choosing another new working copy. Mutating tests verify that originals and backups stay byte-identical.

Windows Microsoft Access comparison has **not** been performed. These checks use Jackcess and UCanAccess independently to reopen native files. They do not verify forms/reports/macros/VBA execution, Access UI parity, live multiuser safety, or the supplied Windows Runtime's exact SQL behavior. Native application-container children and opaque user-table LvExtra/LvModule payloads force the entire copy read only, preserving bytes rather than silently bypassing unsupported behavior. The opaque-payload guard is conservative and does not prove complete detection of every data-macro encoding. Optional object/design suites inspect actual supplied Runtime form/module/report storage read only when ACCESS_RUNTIME_REFERENCE_DIR points to its extracted targets directory; proprietary Runtime files remain outside deliverables.
